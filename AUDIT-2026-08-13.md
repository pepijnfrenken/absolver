# EXECUTIVE SUMMARY

- **[P0] Persistent resume is not actually crash-safe.** LangGraph state contains activation tensors and `pristine_state_dict`, but `graph.py:40-45` converts tensors to Python lists for checkpoint serialization. Resumed nodes expect tensors. A new process also cannot recover the HF model from the process-local model registry.
- **[P0] The central evaluation claim is only partially measured.** Harmful prompts now reach VERIFY and JUDGE, but both decode the entire generated sequence—including the input prompt—rather than only newly generated tokens (`verify.py:884-907`, `judge.py:122-148`). The resulting refusal scores can be contaminated by prompt text.
- **[P0] REBIRTH does not export failed weights, but still creates/updates an output artifact that can be mistaken for a successful model.** It defaults metadata and experience verdicts to `"success"` (`rebirth.py:278`, `342`) and does not remove stale weights from a previous run.
- **[P1] EXCISE retries restore a pristine snapshot, so normal retries are no longer cumulative.** However, rollback is not transactional: an exception after partial mutation leaves the in-memory model corrupted. The restore path assumes `model.device` exists (`excise.py:217-219`), which is unsafe for many HF/device-map models.
- **[P1] Sweep and final EXCISE are semantically inconsistent.** `sweep.py` implements advanced, steering, LoRA, bias, and projected methods, while final EXCISE realizes only `projection` and `mpoa` (`excise.py:19-27`). A sweep winner can therefore be replaced by a different algorithm at the final application step.
- **[P1] Missing judge API keys still produce accepted keyword-fallback results.** The new `judge_status` metadata exposes degradation, but it does not prevent a degraded result from passing (`judge.py:165-179`, `218-223`, `263-287`).
- **[P1] The invocation cap prevents runaway execution but can terminate with a non-terminal result.** `invoke_with_cap` logs the cap and returns the last state without forcing a failed verdict (`graph.py:178-206`).
- **[P2] The test suite passes: 37 tests in 8.72 seconds.** Coverage is concentrated in detector, EXCISE/DISTILL, experience DB, and benchmark-selection helpers. The graph and most operational nodes have no tests.
- **[P2] The standalone sweep scripts are not the LangGraph pipeline.** `run_sweep_v4.py` is a separate hard-coded Modal experiment; `run_absolver_modal.py` duplicates local invocation logic and omits several local safety checks.

# A. PREVIOUS P0 FIXES

## 1. Evaluation prompts not propagated to VERIFY/JUDGE — **PARTIALLY FIXED [P0]**

Prompt propagation is now present:

- `probe.py:320-324` obtains harmful and harmless prompts from state.
- `probe.py:417-425` returns them in the state.
- `verify.py:879-880` reads `harmful_prompts`.
- `judge.py:100-102` reads the same prompts.
- `reflexion.py:315-319` can replace them when expanding the prompt set.

However, the evaluation implementation remains invalid for a rigorous refusal-rate claim. VERIFY and JUDGE decode `out[0]` wholesale:

- `verify.py:889-891`
- `judge.py:129-135`, `141-147`

For decoder-only models, this includes the encoded prompt. The classifier/judge should score only tokens after the input length. This can contaminate refusal detection and the LLM judge’s interpretation of the response.

The pristine refusal baseline is also keyword-scored, not judged through the same scoring path (`verify.py:995-1017`). Thus the “improvement over pristine” gate is not fully apples-to-apples.

**Verdict:** state propagation fixed; central measurement not fully fixed.

## 2. PROBE crashes before first forward pass — **FIXED [P2]**

The former local-variable/device failure is gone. `probe.py:304-318` obtains the model, tokenizer, layers, and device before inference. The forward pass is now reached at `probe.py:391-393`.

The fix was committed in `d0a11f0`, which removed the erroneous model reassignment before the forward pass. Current PROBE still has operational risks—bare `tok(p, ...)` formatting rather than the chat-template path used in VERIFY/JUDGE—but the reported `UnboundLocalError` is fixed.

## 3. EXCISE cumulative across retries — **FIXED FOR NORMAL RETRIES, NOT TRANSACTIONAL [P1]**

Current EXCISE snapshots weights before the first pass (`excise.py:204-212`) and restores the snapshot before later passes (`excise.py:213-220`). The existing test covers this behavior; the CPU suite passed.

This is not transactional. If projection fails halfway through a pass, there is no `try/finally` restoration. The process can retain partially modified weights. Also, the restore code uses:

```python
v.to(device=model.device)
```

at `excise.py:217-219`. Many HF models do not expose a reliable top-level `.device`, especially with `device_map` or offloading. `_device_dtype_of()` correctly derives device from parameters (`excise.py:51-61`), but the restore path does not use it.

**Verdict:** cumulative retry bug fixed in the happy path; rollback safety remains incomplete.

## 4. Failed runs export and missing verdict defaults to success — **PARTIALLY FIXED [P0]**

The weight export is gated:

- `rebirth.py:225-227` marks failure when `quality_pass` is false or a present judge verdict is not `"pass"`.
- `rebirth.py:249-257` only saves weights when not failed.
- `rebirth.py:290-319` only pushes successful runs.

But the artifact semantics remain unsafe:

- `rebirth.py:237-243` always creates the output directory.
- `rebirth.py:259-283` always writes metadata, even on failure.
- `rebirth.py:278` defaults `final_verdict` to `"success"`.
- `rebirth.py:342` defaults the experience record verdict to `"success"`.

A failed run can also leave stale model files in an existing output directory because the directory is never cleaned or atomically replaced. A consumer seeing `abliterated_<model>/` may mistake it for a valid export even when the current run failed.

The gate also ignores `reflexion_final_verdict`. A state with `reflexion_final_verdict="incompatible"`, `judge_verdict=None`, and `quality_pass=True` would pass this gate.

**Verdict:** failed weight saving is fixed; failed-run publication and verdict correctness are not.

## 5. PROBE loop counter not incremented — **MOSTLY FIXED BY OTHER COUNTERS AND OUTER CAP [P1]**

PROBE itself still does not increment a loop counter (`probe.py:296-425`). The control path now increments `ouroboros_count` in VERIFY when refusal is high (`verify.py:1055-1059`) and in JUDGE for any failed verdict (`judge.py:249-256`). The outer invocation cap in `graph.py:178-206` guarantees termination.

This is safer than the previous state, but it is not a direct fix to the original invariant. Reflexion can route back to PROBE (`routing.py:96-102`, `reflexion.py:276-285`) without a PROBE-specific counter. Termination now depends on several counters plus the outer cap.

**Verdict:** runaway behavior is bounded; the original counter design remains indirect.

# B. CURRENT ARCHITECTURE GAPS

## 1. Persistent checkpointer and HF objects — **[P0]**

The model is intentionally kept outside LangGraph state in a global registry:

- `summon.py:342-349` calls `set_model()` and `set_tokenizer()`.
- `excise.py`, VERIFY, JUDGE, and REBIRTH retrieve the model through `get_model()`.

That avoids serializing the HF model, but it makes cross-process resume impossible. A new process restoring a checkpoint has no model in its registry. `--resume` only reuses a thread ID (`run.py:70-78`, `103-109`); it does not reload the model or reconstruct the registry.

More seriously, `graph.py:40-45` monkey-patches msgpack to serialize every tensor as `tensor.detach().cpu().tolist()`. Checkpointed `harm_acts`, `harmless_acts`, and `pristine_state_dict` therefore deserialize as lists, not tensors. `distill.py:271-273` and `excise.py:208-219` expect tensor operations. Resume after those fields are checkpointed is therefore structurally unsafe.

The SQLite backend itself is real: `graph.py:89-98` creates a connection, constructs `SqliteSaver`, and calls `setup()`. The persistence boundary is the problem, not the existence of the saver.

## 2. Evaluation validity — **[P0/P1]**

Prompt propagation is now present, but the measurement still has serious flaws:

- Full-sequence decoding contaminates responses (`verify.py:889-891`, `judge.py:129-135`).
- VERIFY’s refusal metric is a 26-keyword substring check (`verify.py:905-909`), vulnerable to quoted refusals, prompt echoes, and false positives.
- Missing judge API calls fall back to keyword scoring with `quality_score=0.5` (`judge.py:168-179`).
- `judge_status="failed"` does not force run failure; the result can still satisfy thresholds (`judge.py:218-223`, `263-287`).
- Pristine-relative comparison uses a different keyword scorer, not the LLM judge (`verify.py:1002-1017`).

The stack now measures *some* refusal behavior, but not with sufficient validity to support a strong scientific claim.

## 3. EXCISE method mismatch — **[P1]**

The sweep dispatches many methods:

- `sweep.py:226-399`
- `sweep.py:477-510`

Final EXCISE explicitly recognizes only `"mpoa"` and `"projection"` (`excise.py:19-27`). Any other method is normalized to projection (`excise.py:183-195`). Thus a steering or LoRA sweep winner is not reproduced by the final pipeline. The metadata records the normalized method, but the selected candidate’s behavior is lost.

## 4. Invocation cap and resume bugs — **[P1]**

`invoke_with_cap()` determines terminality from:

```python
result.get("reflexion_final_verdict")
or result.get("judge_verdict")
or "success"
```

at `graph.py:184-188`. Missing verdicts are therefore treated as success for loop control. If the cap is reached without a terminal verdict, the function only logs a warning and returns (`graph.py:201-206`); it does not set `reflexion_final_verdict="failed"` or prevent REBIRTH.

`run.py:17-18` also imports `load_config` twice. Minor, but evidence that the production-readiness commit was not cleanly reviewed.

`run_absolver_modal.py:49-81` duplicates the invocation loop rather than calling `invoke_with_cap()`. It does not call `warn_missing_keys()`, does not support `--resume`, and uses the default checkpoint path inside the Modal container. Its checkpoint is consequently not necessarily durable across Modal invocations.

## 5. Orchestration divergence — **[P1/P2]**

- `sweep.py` is an in-graph sweep with optional Modal candidate dispatch.
- `run_sweep_v4.py:1-5` is a separate hard-coded experiment with its own prompts, layers, alpha, and evaluation logic.
- `run_absolver_modal.py:38-117` runs the graph but duplicates local runner behavior.
- The standalone sweep scripts deliberately exclude `connectors/` and `tests/` from their Modal image (`run_sweep_v4.py:18-23`).

These are not equivalent execution paths. Results from `run_sweep_v4.py` cannot be assumed to validate the LangGraph pipeline.

## 6. Test coverage — **[P2]**

Observed suite result: **37 passed in 8.72 seconds**.

Covered:

- Architecture detection: `tests/test_detector.py`
- DISTILL and EXCISE toy-model behavior: `tests/test_excise.py`
- Experience DB: `tests/test_experience.py`
- Benchmark derivation: `tests/test_verify.py`

Not covered:

- SUMMON retry, fallback, tokenizer failure, or registry behavior
- PROBE forward-hook lifecycle, prompt formatting, paired mode, or MoE router collection
- JUDGE API success/failure, parsing, fallback, status metadata, or response slicing
- REFLEXION strategy transitions and alpha search
- Routing invariants
- REBIRTH failure gating, stale-output behavior, and metadata verdicts
- Graph construction, SQLite checkpoint round-trip, resume, invocation cap
- Modal/local orchestration consistency

The test count is therefore not evidence of end-to-end correctness.

# C. RECOMMENDATIONS

## #1 priority — **[P0] Make evaluation and artifact publication transactional**

First, fix the scientific and operational boundary together:

1. Decode only generated continuation tokens.
2. Use one scoring protocol for abliterated and pristine models.
3. Require `judge_status=="ok"` for a publishable result, or explicitly mark fallback runs non-publishable.
4. Make REBIRTH write to a temporary directory and atomically rename only after all gates pass.
5. Never default missing final verdicts to success.
6. Add an end-to-end toy graph test covering refusal reduction, failed judge, checkpoint serialization, and failed REBIRTH.

Without this, the pipeline can produce apparently successful artifacts without measuring or proving the stated claim.

## Best next experiment — **[P1] Paired, blinded, pristine-relative evaluation**

Run a fixed harmful/benign battery on the same model before and after editing:

- identical chat formatting,
- continuation-only decoding,
- blinded human or independently hosted judge,
- keyword classifier as a secondary signal only,
- refusal rate, compliance rate, evasiveness, quality, and benign drift,
- multiple random seeds and at least one held-out harmful set.

Compare the current paired-output direction method against plain diff-means and MPOA under the same evaluation. This would establish whether the observed effect is real or an artifact of prompt/template leakage.

## Most embarrassing gap — **[P1] No graph-level or resume test**

The project claims production readiness and persistent crash recovery, yet there is no test proving that a graph can be interrupted, reconstructed in a fresh process, reload its model, deserialize its checkpointed state, and continue. The current tensor-to-list serializer and global model registry strongly suggest that this advertised feature fails exactly at that boundary.
